# VRM / VRMA (vendored, third-party)

`VRM_VRMA.py` in this directory is vendored **unmodified** from:

https://github.com/MatteoStraccamore/VRM_VRMA

which implements the Velocity Ring Model (VRM) and Velocity Ring Model with
Arcs (VRMA) described in:

> Sylos Labini, F., Straccamore, M., De Marzo, G., & Comerón, S.,
> "Mapping non-axisymmetric velocity fields of external galaxies"
> MNRAS 524, 1560 (2023), arXiv:2306.12902

`vrm_pipeline.ipynb`'s "Figure 8 reproduction" section additionally
implements the rank-correlation / toy-model warp diagnostic from the
companion paper (this is the one originally linked for this task):

> Sylos Labini, F., De Marzo, G., & Straccamore, M.,
> "Breaking the degeneracy between warps and radial flows in external
> galaxies", ApJ 988, 122 (2025), doi:10.3847/1538-4357/adc71c,
> arXiv:2503.22306

The two papers share authors and the VRM/VRMA machinery, but are separate
publications — the first defines the method (and is what `VRM_VRMA.py`
implements), the second builds the warp-vs-radial-flow diagnostic on top of
it (Figure 8 in particular; not implemented anywhere in the vendored code —
see `vrm/bridge.py`'s `run_figure8_analysis`).

**License note:** the upstream repository has no LICENSE file at the time of
vendoring (2026-08). The code is reproduced here for a research comparison
with clear attribution to the authors and source repository; no license
grant beyond that is implied.

## What VRM/VRMA is, and how it differs from this project's own pipeline

VRM fits an ordinary-least-squares model of the same functional form as this
project's harmonic fit,

```
v_los(R, theta) = [v_t(R) cos(theta) + v_r(R) sin(theta)] sin(i) + v_sys
```

but where `harmonic_fit.py` **fixes** the rotation term at Barolo's `VROT`
and only fits `c0` (offset) and `s1` (= `v_r`), VRM fits `v_t` **and** `v_r`
together, per ring, with nothing held fixed except the global geometry
(inclination `i` and position angle). `v_sys` is itself fit once, globally,
by treating the whole map as a single ring (`VRM._OFF`), rather than taken
from the ringlog.

VRMA extends VRM by splitting each ring into azimuthal arcs, fitting an
independent `(v_t, v_r)` per `(ring, arc)` cell instead of per ring — this
recovers a full 2D map of both velocity components rather than a 1D radial
profile, at the cost of fewer points (and therefore more noise) per cell.

Ring geometry is also handled differently: VRM bins in **rescaled** radius
`(R - R_min) / (R_max - R_min)` over the full extent of whatever points are
passed in, not fixed physical ring edges from a tilted-ring model. There is
no equivalent of this project's bootstrap, PA/VSYS degeneracy scan, or
leakage diagnostics — `VRM._matrix()` returns point estimates only, with no
uncertainty quantification of any kind.

**Known upstream quirk:** the constructor accepts a `phi0input` (position
angle) argument, but it is stored and never used anywhere in
`_rescaled_R_theta`. The method silently assumes the input `(x, y)` are
already rotated into a frame where the kinematic major axis lies along
`+x` (the paper confirms this is intentional — the recommended workflow is
to pre-rotate the data by the position angle before calling VRM, not to
rely on `phi0input`). `vrm/bridge.py` in this project does that rotation
explicitly, using the same PA/inclination convention as `harmonic_fit.py`,
so this is handled correctly here — but it is easy to get silently wrong if
you use the upstream class directly and expect `phi0input` to do something.

See `../vrm_pipeline.ipynb` for the actual comparison against this
project's own `s1(R)` result.

## The Figure 8 reproduction (`run_figure8_analysis` in `vrm/bridge.py`)

Reproduces Figure 8 of arXiv:2503.22306 (NGC 2903 in the paper): `v_t(R,θ)`,
`v_r(R,θ)`, and their rank-correlation map, for the observed galaxy and for
a toy/null model; the observed velocity-dispersion map `σ(R,θ)`; and its
rank-correlation with `v_t` and `v_r`. Two things in that paper are not
fully specified in the text, so this implementation makes an explicit,
documented choice rather than silently guessing:

1. **The toy model.** The paper's toy model (Sect. 3, step 2 of the
   procedure summarized on p.11) is pure circular rotation built from the
   TRM's `i(R)`, `φ₀(R)`, `v_c(R)`, with `v_r = 0` — used as a null
   hypothesis to see what the VRM/VRMA pipeline produces when there is *no*
   real radial motion, only whatever artifacts a warped or noisy geometry
   introduces. This project's ringlog has **no warp** (`P.A.`, `INC`
   constant across all four rings, per `CLAUDE.md` Section 4) and Barolo was
   run with `VRAD` fixed at 0 — so `_local_1mom.fits` (`mapset.model_mom1`)
   *is already* exactly that toy model, independently generated by BBarolo's
   own tilted-ring fit. `run_figure8_analysis` reuses it directly (same
   mask, same geometry, run through the identical VRMA call) rather than
   resynthesizing a duplicate mock from the rotation curve.
2. **The correlation "map."** Eqs. 2-3 of arXiv:2503.22306 define a single
   scalar `r_fg` — a sum over *all* cells of a per-cell term, divided by
   `N_cells - 1` (the standard Pearson/Spearman formula). But the
   surrounding text and the Figure 8 caption both call the *plotted*
   quantity a spatial "map" `r_fg(R,θ)`, without writing down a separate
   formula for it. `spearman_correlation_map` in `vrm/bridge.py` uses the
   per-cell term itself (Eq. 3, with ranks instead of raw values) as the
   map — the only quantity defined anywhere in the paper's equations that
   both varies by cell position and whose sum over all cells, divided by
   `N_cells - 1`, reproduces the paper's scalar exactly.

**A real bug this surfaced, fixed in `bridge.py`:** `VRM._matrix()` returns
exactly `0.0` (not `NaN`) for a cell with zero points — a real, finite
number that would otherwise sail straight into the rank-correlation maps
and the residual as if it were a genuine (and, worse, perfectly-fit)
measurement. `run_figure8_analysis` explicitly NaNs out `v_t`, `v_r` (and
everything downstream of them) for any cell below `min_points` (default 3,
the minimum for a determined 2-parameter fit) before computing anything.

**Resolution:** the paper's fiducial grid is `Nr=50, Na=32` on THINGS data.
This dataset has ~440 good pixels total, so `vrm_pipeline.ipynb` uses
`Nr=4, Na=4` and reports `n_points` per cell rather than pretending to the
paper's resolution or statistical power — in particular, the reproduction's
`C_warp` (the analog of Table 1's per-galaxy warp-signature statistic)
should be read as exploratory, not a resolved detection, given how few
cells are usable at this resolution.
